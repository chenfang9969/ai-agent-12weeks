## 0. 四句话总结

1. **模型从不读你的知识库**，它只读"被检索中的那几段"。
2. **切片是检索的原子单位**，这一层丢掉的信息，后面任何一层都救不回来。
3. **三种"像"**：字面像（词频）→ 用法像（向量）→ 意思像（精排）。一层解决上一层，又带来新毛病。
4. **embedding 要用、要懂原理、绝不要复现训练**；真正该亲手写的是 **BM25 和 RRF**。

## 1. 切片的作用 & 模型读取逻辑

### 1.1 核心认知：RAG 不是"让模型查库"

```
用户提问
  ↓
【我的代码】去知识库挑几段（检索）
  ↓
【我的代码】把挑出的几段 + 问题，拼成 prompt
  ↓
【模型】读这个 prompt，组织语言回答
```

模型全程**不知道**你有知识库。它只是个"看着小抄答题"的考生。

- **切片** = 把资料做成一张张小抄卡片（比如每张 ≤400 字）
- **检索** = 从几百张卡片里挑 3 张递给考生
- **模型** = 只看得见递过去的那 3 张

### 1.2 为什么必须切（不直接塞整份文档）

| 原因 | 说明 |
|---|---|
| 装不下 | 真实企业知识库几十万字，超上下文 |
| 会答偏 | 95% 无关内容稀释注意力，反而答不准 |
| 成本 | 每次提问都为全部资料付 token 钱 |
| 没法溯源 | 客户问"哪来的"，说不出是哪份文件哪一节 |

**RAG 存在的根本原因：让模型只读"相关的 1%"，不是"全部"。**

### 1.3 切片大小决定什么

| 切片 | 后果 | 我的实测 |
|---|---|---|
| **太小** | 答案被物理切断 | 100 字切"请假流程"，4 步只装下 1 步，断在"1 天以内由" |
| **太大** | 一张卡混多个主题，分数被稀释 | — |
| **切错位置** | 卡片不是一个完整主题 | Dify 默认按 `\n` 切 → 62 段（平均 26 字）全是标题 |
| **调对之后** | — | 改 `\n\n` → 23 段，平均 72 字，可用 |

> 正则切片只是"在哪下刀"的规则。按 `##` 标题切 = 让每张卡片尽量是一个主题。

## 2. 今天解决的到底是什么问题（词频 → 向量）

### 2.1 原来什么样（失败全过程）

问题：**「产品保修期多久？」**　资料里写的是：**「软件服务期以购买年限为准」**

```
① 拆问题    → "产品""品保""保修""修期"…
② 和卡片比  → 卡片写的是"服务期""服务期内"
              ↑ "保修"和"服务"，一个字都不重
③ 打分      → 0.186（只匹配到"售后"两个字）
④ 门槛 0.25 → 0.186 < 0.25 → 正确答案被当噪声扔掉 ❌
⑤ 模型      → 只看到"产品概述"，只能说"没找到"
```

**根本原因：词频法比的是"字符串是否相同"。** "保修期"和"服务期"在它眼里相似度 = 0。

### 2.2 为什么向量能解决

**核心思想 — 分布式假设：**
> 一个词的意思，由它周围出现什么词决定。（"看他跟谁混"）

```
"服务期" 常出现在 → 以购买年限为准 / 内免费升级 / 内提供支持
"保修期" 常出现在 → 为一年 / 内免费维修 / 过了要收费
                    ↑ 这两组上下文长得极像
```

bge-m3 读了海量中文，统计出"这两个词的用法高度相似" → 所以向量靠近。

**向量是什么**：把一段文字变成 1024 个数字（语义坐标）。意思相近 → 坐标靠近。相似度 = 两坐标的**夹角余弦**（cosine）。

### 2.3 关键转变

| | 词频法 | 向量法 |
|---|---|---|
| 比什么 | **字符是否相同** | **用法是否相似** |
| 保修期 vs 服务期 | ≈ 0（没一个字相同）| **0.6635** |
| 我的实测 | 0.186，被门槛砍掉 | **第 1 名，答出来了** |

### 2.4 但向量带来新问题（这才是重点）

```
年假规定   0.5626
正确答案   0.6635   ← 只差 0.1
```

**为什么"年假"也这么高**：因为"入职满 **1 年**"和"服务期以购买**年限**为准"都有"年/期限"的语感。

**向量的性格：宁可多拉，不肯漏掉。** 救回了正确答案，代价是把错的也拉近了。

**而且分数挤在 0.5~0.7（跨度只有 0.14），没法像词频法那样"0.25 一刀切"。**

### 2.5 于是有了第三层：LLM 精排

精排不是比距离，是**让模型真的读一遍**：

```
问题：产品保修期多久？
资料：软件服务期以购买年限为准…
这段能不能回答问题？0-10 分
```

实测结果：

| 分 | 片段 |
|---|---|
| **3** | 产品资料 · 保修与售后 ← 含答案 |
| 0 | 员工手册 · 考勤与请假 |
| 0 | 产品资料 · 产品概述 |
| 0 | 销售资料 · 常见异议应对 |

**区分度完美**（3 vs 全 0），因为模型懂"服务期 ≠ 保修期"，所以只给 3 分（"有关但答不全"）。

**⚠️ 坑**：门槛设 5 分 → 3 分也被杀 → 全拒答。**门槛必须降到 3，或用相对排序。**

### 2.6 最终跑通

```
vec top-6 → 精排门槛 3 → 只留 1 条（就是含答案那条）→ 排第 1 名 ✅
```

### 2.7 三层"像"总表

| 层 | 比什么 | 我最关键的数字 | 性格 | 毛病 |
|---|---|---|---|---|
| ① 词频 | **字面像** | 0.186（第2）| 精确、可解释、便宜 | **漏同义词** |
| ② 向量 | **用法像** | 0.6635（第1）| 召回广、能救同义 | **噪声大、没法设阈值** |
| ③ 精排 | **意思像** | 3分 vs 全0 | 区分度极好 | **慢、贵、打分保守** |

> **每一层都在解决上一层的问题，又带来自己的新问题。**

### 2.8 诚实提醒

这次成功有"调参凑巧"成分：精排给 3 分，门槛正好设 3。
换个问题若正确段 3 分、无关段也 3 分 → 就分不开了。

**更靠谱：相对排序**
```
❌ ≥3 分就留
✅ 永远取最高 1-2 条，且要求第1名明显高于第2名
```
（和 W03 的「绝对 0.25 + 相对 45%」是同一个思想）

## 3. RAG 检索的底层原理与实现方案

### 3.1 本质只有一件事

> **把「问题」和「每段资料」变成可比较的形式，然后算谁更近。**

区别只在"变成什么形式"和"怎么算近"。

### 3.2 三条血统

| | 稀疏（BM25/TF-IDF）| 稠密（向量/双塔）| 交叉（精排）|
|---|---|---|---|
| 形式 | 词→权重的字典 | 1024 维坐标 | 整体过模型 |
| 能预计算 | ✅ | ✅ | ❌ |
| 中文同义词 | ❌ 完全不行 | ✅ 强 | ✅ 强 |
| **精确匹配（型号/编号）** | ✅ **强** | ❌ 弱 | ⚠️ 中 |
| 速度 | 极快 | 快 | 慢 |
| 成本 | ≈0 | 低 | 高 |
| 位置 | 第一层 | 第一层 | 最后一层 |

**双塔为什么是"双"**：问题和资料走两个独立编码器 → **资料可以提前全部算好存起来（离线）**，查询时只算问题（在线）。这是它能上生产的前提。精排只有一个塔（拼一起过），所以**不能预计算**，只能用在最后一步。

**对比学习怎么训 embedding**：
```
正样本 ("保修期多久", "服务期内免费维修")  → 拉近
负样本 ("保修期多久", "员工年假规定")      → 推远
重复上千万次
```
**它不是"理解了语言"，是被拉近推远了几千万次。**

### 3.3 BM25 的两个关键改进（我现在的 TF-IDF 还没做）

| 改进 | 含义 | 为什么重要 |
|---|---|---|
| **TF 饱和**（k1）| 一个词出现 10 次 ≠ 重要 10 倍，超阈值饱和 | 防"服务"刷屏的段落霸榜 |
| **长度归一化**（b）| 长文档天然命中更多词，要打折 | 我现在只有 `sqrt(len)` 粗略版 |

### 3.4 索引怎么存和查

**倒排索引（稀疏用）**：`"服务" → [doc1:2, doc3:5, doc7:1]`
查询时直接跳到这个词那行，不扫全部文档。

**ANN / HNSW（向量用）**：
```
上层：稀疏"高速公路"图 → 快速跳到大区域
下层：稠密"小巷"图     → 附近精找
```
代价：**是近似搜索，可能漏掉真正的第一名**。用速度换精度。
（Dify 默认的 Weaviate 就是这套；我现在 23 段用暴力扫也行，所以察觉不到）

### 3.5 完整流水线

**建库（离线）**：解析 → 清洗 → 切块 → 向量化+稀疏化 → 建索引

**查询（在线）**：
```
问题 → 查询改写 → 多路召回(BM25 20条 + 向量 20条)
     → 融合(RRF) → 精排(留3-5条) → 组装上下文 → 生成+引用
```

### 3.6 进阶手段（知道有就行）

| 手段 | 解决什么 | 要不要学 |
|---|---|---|
| **父子块**（small-to-big）| 小块检索准，父块给模型全 | ⭐ 实用 |
| **RRF 融合** | 稀疏+稠密合并排序 | ⭐⭐ **必学** |
| HyDE | 先编假答案再检索 | 一般 |
| GraphRAG | 跨文档关系推理 | 现在用不上 |
| 上下文压缩 | 长候选压短 | 进阶 |

### 3.7 我的项目对照（6/8）

| 环节 | 状态 | 文件 |
|---|---|---|
| 解析清洗 | ⚠️ 简化 | — |

## 4. Embedding 要不要学习复现

### 4.1 结论

| 层次 | 要不要 | 为什么 |
|---|---|---|
| **① 会用**（调 API、算 cosine）| ✅ **必须** | 已经在用 |
| **② 懂原理**（分布式假设、双塔、对比学习）| ✅ **必须，能白板画** | 客户/面试问"为什么懂同义词"，得答得出 |
| **③ 从零训练模型** | ❌ **绝不要** | 投入产出比极差 |

### 4.2 为什么不要复现训练

1. **门槛在数据和算力，不在代码**
   需要千万级三元组 + 多卡训几周。代码部分 `sentence-transformers` 十几行就写完。
2. **别人已经免费做到你追不上**
   `BAAI/bge-m3` 中文 SOTA，API 调用 0 元。你训半年不如它。
3. **我的目标是赚钱，不是发论文**
   竞争力在"选哪个、怎么切、怎么调、怎么评估、怎么解释"。

### 4.3 判断准则（以后所有技术都适用）

> **凡是"调用能解决"的，绝不造轮子。**
> **凡是"决定效果好坏"的，必须懂到能调。**

- embedding 模型本身 → 调用解决 → 不造
- 切块、融合、门槛、rerank → 决定效果 → 必须懂

### 4.4 值得亲手写的三个（每个 30-60 分钟）

| 优先级 | 写什么 | 能学到什么 |
|---|---|---|
| ⭐⭐⭐ | **BM25**（约30行）| TF 饱和 + 长度归一化的实际效果 |
| ⭐⭐⭐ | **RRF 融合**（约20行）| 只需排序结果，不需要分数量纲一致 |
| ⭐ | 最小 embedding 推理（20行）| 亲眼看到"文字 → 矩阵" |

**RRF 核心 6 行**：
```python
def rrf(rank_lists, k=60):
    score = {}
    for ranks in rank_lists:
        for rank, doc_id in enumerate(ranks, 1):
            score[doc_id] = score.get(doc_id, 0) + 1 / (k + rank)
    return sorted(score, key=score.get, reverse=True)
```

## 6. 如果只记三句话

1. **模型不读你的库，只读被检索出的那几段 → 所以切片是原子。**
2. **词频看字，向量看用法，精排看意思 → 三层的毛病各不相同，不能互相替代。**
3. **embedding 用现成的；自己动手写 BM25 和 RRF。**
